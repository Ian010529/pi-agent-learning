Lesson 01 · Pi Agent · prepared 2026-10-06

Minimal Agent Loop

本课只解决一个问题：去掉 TUI、skills、MCP、session 等外围后，Pi 的通用 Agent 到底怎样完成一次 “LLM → tool → result → LLM” 闭环？

完成标准

不看资料，能从一次 toolCall 开始，准确说明 Pi 如何执行工具、产生 ToolResultMessage、为什么会再次请求模型，以及什么时候自然停止。

1. Technical Foundation

1.1 LLM 不是 Agent

这一课只保留最小区别：

LLM:
  transcript/context
      ↓
  assistant message

Agent runtime:
  准备 context
      ↓
  调 LLM
      ↓
  解析 assistant message
      ↓
  如有 tool call → 执行 → 写回 result
      ↓
  决定是否再发起 provider request

因此 “LLM 会调用工具” 的准确含义不是模型自己执行函数，而是模型输出一个结构化的 toolCall；runtime 验证并执行。

1.2 Turn 与 Loop

Pi Agent Core README 把一个 turn 描述为：一个 assistant response 加上它产生的 tool executions/results。一次用户任务可以包含多个 turn。

turn 1:
  assistant(toolCall)
  → tool result

turn 2:
  assistant(toolCall)
  → tool result

turn 3:
  assistant(text)
  → no automatic tool continuation

1.3 Context / Transcript

AgentContext 中最重要的两项是 messages 和可执行 tools。在 provider request 前，Agent messages 会经过 transform/convert，成为模型能理解的 transcript。

1.4 Tool protocol

在当前 types.ts 中，AgentTool 至少提供 schema/metadata 和 execute(...)；执行后返回 AgentToolResult。模型真正看到的是 result 的 model-facing content。

1.5 Termination：先别把它理解成 “finished=true”

正常情况下，loop 的自然 continuation 主要来自 tool result、steering/follow-up 或显式 continuation hook。没有这些 continuation 时 run 才结束。当前源码另外允许 finishTurn 明确返回 { action: "end" } 或 { action: "continue" }，所以不能把 Pi 简化成“模型回答 finished=true 就退出”。

3. Source Walkthrough

3.1 types.ts：先看 runtime 合同

AgentContext {
  messages: AgentMessage[]
  tools?: AgentTool[]
}

AgentTool.execute(...)
  → Promise<AgentToolResult>

AgentToolResult {
  content
  details
  isError?
  terminate?
  ...
}

读这部分时只问两个问题：模型能请求什么？runtime 最后必须回灌什么？

3.2 agent.ts：Agent 是 stateful wrapper

源码注释直接把 Agent 称为 “Stateful wrapper around the low-level agent loop”。它持有 transcript、tools、streaming 状态，以及 steering/follow-up queues；真正的低层调度则交给 runAgentLoop/runAgentLoopContinue。

3.3 agent-loop.ts：入口

runAgentLoop(...)
  ├─ 把新 prompt 加入 currentContext
  ├─ emit agent_start / turn_start
  └─ runLoop(...)

3.4 runLoop()：真正的循环

当前源码是 outer loop + inner loop。第一课先只关注最核心的 natural continuation：

while (true) {                       // outer
  while (hasMoreToolCalls || pendingMessages.length > 0) {
    ...
    assistant = streamAssistantResponse(...)
    toolCalls = assistant.content.filter(type === "toolCall")

    if (toolCalls.length > 0) {
      results = executeToolCalls(...)
      append results to context
      hasMoreToolCalls = !batch.terminate
    }

    finishTurn(...)
    poll steering
  }

  poll follow-up
  if (follow-up exists) continue

  if (explicitContinuation) continue

  break
}

3.5 Provider boundary

streamAssistantResponse() 在真正调用模型前做两步：

AgentMessage[]
  ↓ transformContext?()
AgentMessage[]
  ↓ convertToLlm()
Message[]
  ↓ normalizeContext()
TranscriptContext
  ↓ streamFunction(model, context)
AssistantMessage stream

这条边界很重要，但为什么要把 provider/model 再拆成 packages/ai，留到 Lesson 02。

3.6 Tool branch

assistant message 出现 tool calls 时，Pi 会进入 executeToolCalls()。当前实现支持 parallel/sequential；但无论哪种模式，本课只抓共同语义：

assistant toolCall
  ↓
arguments validation / preflight
  ↓
tool.execute(...)
  ↓
finalize result
  ↓
ToolResultMessage
  ↓
append to currentContext.messages
  ↓
下一 turn 的 provider request 可以看到 result

4. Execution Trace

假设用户说：

“告诉我 config.json 里的 model 是什么。”

模型第一次没有直接回答，而是产生：

toolCall: read({ path: "config.json" })

源码级 mental trace：

① user message 已进入 context

② streamAssistantResponse()
   → provider 返回 AssistantMessage(toolCall)

③ runLoop() 取出 toolCalls

④ executeToolCalls(...)
   → 找到名为 read 的 executable tool
   → 参数校验
   → read.execute(...)

⑤ tool execution 得到 result
   → 转为 ToolResultMessage

⑥ ToolResultMessage append 到 currentContext.messages

⑦ hasMoreToolCalls = true（除非整个 batch 明确 terminate）

⑧ 进入下一 turn
   → provider request 包含之前 assistant toolCall + tool result

⑨ 模型现在根据文件内容回答：
   “model 是 ...”

⑩ 如果没有新的 tool call、没有 steering/follow-up，
   且 finishTurn 没要求 continue
   → run 结束

5. What the video can help with — and where to be careful

上传字幕对“LLM → tool → result → LLM”的直觉有帮助。但课程不会把视频口述中的“模型判断完成就结束”直接当作当前实现。当前源码存在 finishTurn、tool-result continuation、steering/follow-up 等更精确的 scheduling 语义。

6. Practice

不要看上面的 execution trace。给定 assistant 输出：

{
  type: "toolCall",
  name: "read",
  arguments: { path: "config.json" }
}

请自己写出从这条 toolCall 到下一次 LLM request 之间至少 5 个步骤，并说明每一步是“模型做的”还是“Agent runtime 做的”。

Learning Gate 01

闭卷回答，允许用自己的语言：

  1. Boundary：为什么 “LLM 调用了 read 工具” 这句话技术上不够精确？
  2. Execution：从 assistant 产生一个合法 toolCall 开始，到模型拿到 tool result 为止，按顺序说出执行链。
  3. Termination：为什么 “Pi 每轮都会问模型 finished 了吗” 不是当前源码的准确描述？至少说出一种自然 continuation 和一种显式控制机制。
  4. Transfer：如果你自己写 mini-Pi，为什么不能只写 while(true) { callLLM() }？你至少还必须维护什么状态/协议？

通过标准：不是关键词全对，而是能正确区分 model 与 runtime，并能恢复因果顺序。通过后才创建第一条 learning record。
